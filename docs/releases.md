# 版本与打包

`v1.0.0` 是首个正式源码版本，在 `v0.1.0` 公开基线上整理目录配置、业务包、工作台和文档。版本号保存在 `VERSION`，变化记录在 [版本记录](changelog.md)。对应标签使用 `v<版本号>`。已有 `version1`、`version2` 分支是历史开发快照，保留其历史；正式发行编号从 `v1.0.0` 开始。

v1 通过本机 Streamlit 服务使用。原生 macOS App、桌面安装包和服务生命周期整合属于下一版本；尚未完成的前端草稿不作为 v1 的已交付功能。

## 发布检查

在不含私人数据的源码工作区执行：

```sh
.venv/bin/python -m unittest -q
.venv/bin/python scripts/check_public.py
git diff --check
```

测试使用合成输入和临时数据，覆盖台账、模型适配、队列、归档、路径配置及工作台。CI 在 Linux 运行无模型测试与当前源码检查，不验证 Apple GPU 推理。模型效果和桌面运行情况仍需在本机确认。

推送后必须确认 GitHub Actions 检查通过，再将该提交标记为正式发布。线上检查失败时先修复，并保留已公开标签；补丁使用新版本号，避免覆盖他人已取得的发布内容。

提交前核对文件清单、README 和 `VERSION`。只提交源码、通用文档和合成测试；本机 `paths.json`、台账、媒体、转写与草稿不能因整目录添加而混入发布。

## 打包源码

在已提交且工作树干净的发布版本上执行：

```sh
.venv/bin/python scripts/build_release.py
```

输出在项目的 `.local/releases/`，包含 `echo-<版本号>.tar.gz` 和 SHA256 校验文件。只打包当前 `HEAD` 的文件，不带 `.git` 历史、录屏、转写、模型或本机配置。打包器会拒绝未提交或未跟踪文件；若需要保留下一版本草稿，可在隔离的干净发布工作树构建。

核对压缩包清单与校验文件后，把正式提交和版本标签推送到项目的 GitHub 仓库。源码包可以作为对应版本的附件，不能标为已签名的 macOS App 安装包。

## 历史审查

当前公开仓库已从 `v0.1.0` 建立独立历史，后续正式版本可沿用这个公开基线。未知的私有开发历史仍需单独审查，不能因为当前文件检查通过就一并公开。

```sh
.venv/bin/python scripts/check_public.py --history
```

历史扫描额外检查提交邮箱，并将旧 `PROJECT_CONTEXT.md` 标为人工复核项。v1 发布准备已人工阅读 `d336a42267ac` 与 `268fac8bfe92` 中的两份文件：内容为通用开发约定，没有发现真实面试资料、私人机器路径或凭据。这两个启发式命中会使 `--history` 返回失败；应保留实际检查结果与人工结论，不能把它报告为全量扫描自动通过。

如导入其他私有分支，或改变现有仓库可见性，还需检查其提交、分支、标签和平台附件。新建公开仓库时，可用无历史源码包初始化，并使用 GitHub noreply 提交邮箱。
